# 澎湃补全计划 · HyperExtend

把散落在若干个小模块里的澎湃 OS（HyperOS）补全功能，收进**一个** LSPosed 模块、**一套**开关面板。

一个 APK、一份作用域列表、一次重启，就能同时拿到状态栏、通知、控制中心、锁屏、
多任务窗口等各处的小修小补 —— 不必为每个小功能各装一个模块、各配一次作用域、各重启一遍。

| 项 | 内容 |
| --- | --- |
| 基准平台 | 澎湃 OS 4（Android 16） |
| 技术栈 | libxposed API 102 + miuix（HyperOS 风格 Compose UI） |
| 当前版本 | `0.1.5`（versionCode `6`） |
| 作用域 | 10 个宿主进程（见 `META-INF/xposed/scope.list`） |
| 功能条目 | 95 条，全部默认关闭 |
| 许可 | AGPL-3.0 |
| 下载 | [Releases](https://github.com/YGHFv/Hyper-Extend/releases)（由 CI 自动发版） |

## 为什么要有这个模块

这些功能原本各自是一个独立模块：每一个都要单独安装、单独在 LSPosed 里启用、单独配作用域。
功能本身都很小，但模块数量一多，维护成本（跟进每个上游、每个 ROM 版本、每次都重启）就盖过了功能价值。

本模块把它们聚合到一处，并共用同一套基础设施：

- **统一的开关面板**：按作用域收纳，找不到的靶子只记日志不报错，不会因为一个功能失效而拖垮整页。
- **统一的安全底线**：默认全关、不认识的宿主一概不碰、注入侧不许抛异常，外加两级逃生门（见「防砖」）。
- **统一的工程约束**：设置键就是功能 id，加一个功能只改一处目录，界面、搜索、存取自动跟上。

## 功能一览

下面的分组与应用内的面板分组一一对应（见 `core/FeaturePanels.kt`）。全部条目默认关闭。

### 通知

- **解锁通知重要程度** —— 长按通知调整渠道重要程度；菜单可跳应用设置或对应渠道
- **移除通知数量限制** —— 不因单应用通知过多自动清除旧通知
- **自动展开指定应用通知** —— 自动展开通知内容和固定悬浮通知
- **自动收起展开的悬浮通知** —— 展开后按设定时间结束悬浮显示，不删除通知

- **修复勿扰模式下通知提示** —— 开启勿扰时抑制系统界面的通知声音、振动和提示灯
- **亮屏时静音** —— 亮屏时禁止通知发出提示音

## 界面

底栏三页：

- **首页** —— 按**作用域**（被注入的宿主应用）收纳成入口行。每行带宿主的真实图标、
  「已启用 n / m」，以及未安装时的明确标注。点进去是该作用域下的功能开关。
  系统框架（system_server）第一、系统界面第二，其后依次为截屏、设备互联、小米互传和小米智能卡。
- **设置** —— root 权限检测、批量启用/关闭、恢复默认设置。
- **关于** —— 模块状态、开源致谢、日志与紧急停用。

功能按面板分组呈现（上一节的分组就是界面上的分组）。只有一个开关的功能直接在列表中操作；
包含子选项、参数、图片或附加配置的功能保留二级入口，搜索结果采用同一规则。

**每个功能只在界面上出现一次。** 通行密钥同时在系统设置、安全中心、扫描器和系统框架里生效，
但它只显示在**系统框架**下面 —— 同一个开关在四个入口里各出现一遍，用户只会以为那是四件事。
归属规则：功能 `scopes` 列表里第一个宿主就是它的入口，所以主宿主写在最前；
跨宿主的完整清单在功能详情页的「生效范围」里如实列出。

### 让改动生效

每个作用域页面的**右上角是「让改动生效」按钮**（全页仅此一个）。开关的值是宿主进程**启动时**
读进内存的，所以改完必须让宿主重新读一遍；这个按钮就是做这件事的。

模块不再支持热重载：自动热重载已关闭，框架热重载请求会被拒绝。更新模块或修改设置后，
请重启对应宿主进程。系统框架只能随设备重启生效，需要用户明确确认；模块不会自动重启设备。

结束进程需要 root（结束别人的进程要 `KILL_ANY_PROCESS` 级别权限，普通应用拿不到），
失败时界面会如实说明是「没有 su」「授权被拒」还是「超时」—— 这三者的补救动作完全不同。
「设置」页有一项 root 检测，可以先把这件事查清楚。

## 作用域

`app/src/main/resources/META-INF/xposed/scope.list`：

```
com.android.systemui            状态栏 / 通知 / 控制中心 / 锁屏 / 窗口 / 手势横条
system                          通行密钥、旋转锁定等系统服务侧修复
com.android.settings            通行密钥的默认凭据提供方、通知重要程度跳转
com.miui.securitycenter         通行密钥的配置保护
com.xiaomi.scanner              通行密钥的扫描器调用方
com.miui.tsmclient              NFC 卡面
com.miui.screenshot             截图自动复制到剪贴板
com.milink.service              剪贴板读取崩溃保护
com.miui.mishare.connectivity   小米互传接收文件索引冲突修复
com.miui.misound                分应用音量面板数据源
```

`staticScope=true`：作用域由模块自己声明，用户在 LSPosed 里加不了作用域之外的包。
模块界面应当至少打开过一次（让模块脱离 stopped 状态）。

### 小米互传接收文件索引冲突修复

默认关闭，入口为 **小米互传 → 接收文件索引冲突修复**。必须在**接收文件的手机**上
安装模块、启用 LSPosed 的 `com.miui.mishare.connectivity` 作用域、打开开关并让改动生效。
只在发送端打开不能修复接收端的存储问题；重启互传进程前请结束正在进行的传输。

故障形态是：`Download/MiShare/base.apk` 不存在，但 MediaStore 仍有同路径记录；
原生接收器创建文件得到 `EEXIST`，随后发送端显示通用失败。并非所有重名文件都失败，
也不是发送端文件管理器改名就一定能解决。

模块采用更保守的自动规避：在接收器把路径交给回调和原生层**之前**，只读检查该路径。
仅当文件确实不存在、媒体库仍有记录时，选择例如 `base (HE-0123456789ab).apk` 的备用名，
再次检查文件系统和媒体库均未占用后交还宿主。保留扩展名，按 UTF-8 的 255 字节上限裁剪过长主文件名。
不清媒体库、不申请额外权限、不创建占位文件、不修改文件内容，也不主动覆盖已有文件。

运行要求 Android 11+，不按小米互传的版本名或版本号限制启用；当前使用从
`3.4.1 / 30401`、`5.4.2_20260923_1315 / 50402` 核对出的两组接收调用目标，按完整方法签名成对匹配。
仅处理当前用户主存储的 `Download/MiShare` 直接子文件，其他保存目录与其他调用方保持原行为。
索引查询无权限、状态不明或候选耗尽时也保留原行为。

### 截图自动复制与设备互联保护

两个默认关闭、可独立使用的开关：

- **截屏 → 截图自动写入剪贴板**：解锁截图应用的原有自动复制逻辑。
  不校验截图应用版本号，改为核对目标类与方法签名；目标不匹配时跳过并记录日志。
- **设备互联 → 剪贴板读取崩溃修复**：在 `FileUtil.isAvailableUri(Uri, Context)`
  捕获媒体状态、权限与 I/O 异常，将不可读图片判为不可用。可独立配合西米露使用。

截图原实现会在输出流关闭和 MediaStore 发布之前写入剪贴板，此时图片仍为 `IS_PENDING=1`。
本模块不强行清除媒体状态、不放宽权限，而是异步等待 `IS_PENDING=0` 且 `IS_TRASHED=0`
后才复制；最多等待 15 秒，失败或超时跳过。

### NFC 卡面列表

卡面列表来自钱包实际加载过的图片，不扫描钱包的全部私有目录。更新模块后，让「小米智能卡」
作用域的改动生效，再进入钱包的卡片列表或卡面页；回到模块的卡面自定义页面查看，必要时下拉刷新。

钱包 Hook 在自己的进程里读取本地图片并生成缩略图，通过仅接受钱包 UID 的 Provider 回传模块；
模块直接读取自己的缓存，不使用 `su` 跨 UID 读取钱包文件。当前按原始卡面地址分别保存替换图片，
每个条目点击右侧图片选图，长按已选择的图片清除此卡的替换映射。

## 防砖

作用域里有 `system`（system_server），所以「最坏情况」是开机循环。五层防线：

**① 默认全关（最重要的一层）。** 所有布尔功能主开关默认关闭，读不到设置或设置类型错误也按关闭处理。
NFC 卡面为配置型功能，保留只读采集 Hook，不属于布尔主开关；未配置时不替换卡面。

这一层有一条容易写错的细节：功能有主开关与子项两级，而有的 hook 点是直接按子项 id 判断的。
子项默认值是「开」（主开关一打开，子项就该全部生效），于是**只读子项那个键就会在用户从没进过界面的
情况下读出 true**。`HookSettings.isOn` 因此在内部强制「子项必须同时满足所属功能的主开关」。

**② 不认识的宿主一概不碰。** 每个功能装 hook 前先确认宿主对不对：
系统界面侧的功能要求存在 `miui.os.Build`（即确实是小米 ROM）；通行密钥的靶子
`RequestSession` / `IntentFactory` 是 **AOSP 类**，在类原生系统上挂它们会把凭据会话
错误地指向 Google GMS —— 那属于「修出一个原本不存在的故障」。
目标类/方法找不到时一律「记日志 + 跳过」，绝不报错。

**③ 异常保护。** `HookRuntime.hook` 对每次宿主调用保存结果：模块前置处理出错时调用原方法一次，
后置处理出错时保留原结果（含 void/null），不重放宿主副作用。宿主自己抛出的异常按原语义传回。
API 102 使用 `PASSTHROUGH`，模块错误由自己的保护层处理。

**④ 逃生门（恢复模式可用）。** 万一真进了开机循环，系统进不去 → 模块界面和 LSPosed Manager
都打不开，界面上的「停用」按钮恰好够不着。所以提供两个**不需要开机即可生效**的标记，
任何一个成立，所有 hook 一律不装：

```
# 方式一：属性（需要 root，persist. 前缀保证重启后仍生效）
adb shell su -c 'setprop persist.sys.hyperextend.disabled 1'

# 方式二：文件
adb shell touch /data/local/tmp/hyperextend.disabled
adb shell mkdir -p /sdcard/HyperExtend && adb shell touch /sdcard/HyperExtend/disable
```

撤销：属性设回 `0` 并删除已设置的文件标记，重启即可。属性读失败时不安装 Hook；
文件标记在部分 SELinux/存储环境不可读，优先使用 root 属性方式。**不需要卸载模块、不需要清 LSPosed 数据。**

框架启动保护是**另一条独立的持久标记**，别把它和上面那条混为一谈：
`persist.sys.hyperextend.disabled` 管的是「所有宿主一律不装」，而
`persist.sys.hyperextend.framework_disabled` 由 `BootLoopGuard` 在系统框架连续重启时自己 arm，
只停用系统框架（并连带停用系统界面），清掉前一条不会解掉它。恢复时把该属性设回 `0`：

```
adb shell su -c 'setprop persist.sys.hyperextend.framework_disabled 0'
```

并删除状态文件 `/data/system/hyperextend_bootguard`，重启即可恢复系统框架；系统界面随后会自动跟上。
两条标记各写各的，任何一条读到 `1` 或读不出来，对应一侧就不装 Hook。

**⑤ 安全模式与自动防砖。** 在「设置 → 故障排查 → 安全模式」按宿主查看图标、包名和开关。
开关开启表示停用该宿主的模块功能，不清空功能配置；关闭需要确认，随后重启对应宿主（系统框架需重启设备）。

`system_server` 与 `SystemUI` 分别记录启动，首次启动不算重启；同一五分钟窗口内三次重启（第四次启动）
触发持久保护。框架启动保护仍同时禁止 SystemUI；SystemUI 独立保护只停用自身。
其他宿主可手动停用，或在被保护的 Hook 执行异常时自动停用。状态采用同目录临时文件、同步写入后替换；
坏文件、IO 失败和异常时钟均跳过 Hook。正常运行或重启不能自行解除已触发的保护。

异常先保存在宿主私有目录，再异步报告模块；模块前台收到时弹窗，后台事件留到下次打开，不从后台拉起界面。
已修改的界面和已注册的异步监听仍可能需要重启才能完全清理。系统框架启动保护触发时，先恢复系统框架并重启设备，
再恢复被连带保护的系统界面。

实现见 `hook/BootLoopGuard.kt` 与 `hook/KillSwitch.kt`。

**桌面原生原型不等同于上述保护。** 原型入口已接只读安全预检：检查配置快照、
现成本地熔断状态和两种时钟。独立持久化后端与受控武装/残留恢复事务已有离线故障测试，
持久化启动事务已经接入原型入口；受控武装/残留恢复仍没有接入，也没有生产授权方。
普通配置通道的恢复令牌固定为 `0`，不借用框架或其他宿主的恢复令牌；
原生预检与独立启动事务也拒绝非零恢复令牌，不只依赖发送端自律。
防砖一致性审计现已含完整链路验证器（从导出入口可达性、快照用途门禁、提交控制流、
安装支配、失败阻断、安装点唯一性与分支极性），并已按 49 条假绿路径逐条加固与回归；
可达性用三值常量求值加语句级分析，`if constexpr (false)`、宏恒假条件、
常量 `switch` 不匹配分支、无 `break` 的死循环之后等都算执行不到。
门禁、提交守卫与安装许可判定要**无条件支配**其后环节：早退必须自身可达、
真分支必然终止且真的跳过安装；安装点必须落在必然执行的位置，提交结果在守卫前
被改写也不算数；三处守卫的极性改用符号化蕴含判定，被额外合取条件削弱的写法不再翻绿。
实测结构接线已通过离线审计；真实设备上的安全、并发和代码页验收仍未完成，缺口如实保留。
桌面主开关也不授权初始化、解除熔断或清理残留文件，专用恢复流程尚未实现。
即使计算结果正常，
仍保留持久化阻断与安装阶段锁；`防砖已确认=false`、`安装许可=false`。
普通构建不打包此原型。细节与离线测试见 `app/src/main/cpp/README.md`。

## 下载

不必自己编译：每次推送 `main` 后 CI 都会跑单测并打包 release APK（见 Actions 工件），
当 `app/build.gradle.kts` 里的 `versionName` 变化时，CI 自动建 `v<版本号>` 标签并
发到 [Releases](https://github.com/YGHFv/Hyper-Extend/releases)。直接装那里的
`app-release.apk` 即可，与本地 `:app:assembleRelease` 的产物同源同签名，可直接覆盖安装。

## 构建

```
./gradlew :app:assembleRelease
```

**发布用 release，不要用 debug。** 模块的 dex 会被注入宿主进程（SystemUI、system_server），
debug 构建既没有 R8 压缩也不做优化，往每个宿主进程里塞一份几 MB 的未压缩 dex，
表现为「启用模块后整机发卡」；模块界面本身也会明显迟滞。release 走 R8，
`app/proguard-rules.pro` 里保住了入口类与 provider。

要求：

- JDK 17
- Android SDK：`compileSdk 37` / `minSdk 26` / `targetSdk 35`
- `local.properties` 里的 `sdk.dir` 指向本机 Android SDK

依赖里有一处是**硬约束**：`io.github.libxposed:api` 必须是 `compileOnly`。
它以及全部宿主类型都只存在于被注入的进程；打成 `implementation` 会让模块进程里
加载到一份假的 API 实现（或直接 `NoClassDefFoundError`）。
所有宿主类型一律走反射（见 `hook/Reflect.kt`），不要 `import`。

## 工程结构

```
app/src/main/
├── java/io/github/YGHFv/HyperExtend/
│   ├── HyperExtendApplication.kt     模块 App 进程：接上框架服务、投影设置
│   ├── core/
│   │   ├── FeatureCatalog.kt         功能目录 —— 界面的唯一数据源（功能 → 作用域）
│   │   ├── ScopeCatalog.kt           作用域目录 —— scope.list 在界面上的化身
│   │   ├── FeaturePanels.kt          面板分组 —— 功能一览里那些标题
│   │   ├── OpenSourceProjects.kt     开源致谢清单
│   │   ├── FrameworkBridge.kt        框架服务（XposedService）的唯一持有者
│   │   └── ModuleLog.kt              日志（logcat + 内存环形缓冲，两个进程各一份）
│   ├── config/HyperSettings.kt       模块侧设置读写（本地 prefs 权威 + 投影给框架）
│   ├── ui/                           主界面（miuix / Compose），只在模块进程中运行
│   └── hook/                         被注入进程里的一切
│       ├── HyperXposedEntry.kt       入口（java_init.list 指向它）
│       ├── HookDispatcher.kt         按宿主包名分派功能
│       ├── HookRuntime.kt            挂 hook 的统一出口（失败绝不冒泡）
│       ├── KillSwitch.kt / BootLoopGuard.kt   紧急停用与自动防砖
│       ├── Reflect.kt / DexScan.kt   宿主反射 / 类名兜底扫描
│       └── feature/                  按宿主分目录的功能实现
└── resources/META-INF/xposed/        module.prop / scope.list / java_init.list
```

`FeatureCatalog.kt` 与 `ScopeCatalog.kt` 之间的**双向引用**（功能声明它在哪些作用域里，
作用域反查它有哪些功能）是刻意的：界面两个方向都要用，而两份都是纯数据、无副作用。
加功能时只改 `FeatureCatalog.kt`，加宿主时只改 `ScopeCatalog.kt`。

## 排查

- **开关拨了没反应**：先看「关于」页里的「框架服务」是否已连接。
  未连接 = 设置推不到注入侧（LSPosed 未启用模块，或模块不在作用域里）。
  已连接的话，多半是宿主进程还没重新加载 —— 进对应作用域页，点右上角那个按钮。
- **某个功能不生效**：看「已捕获异常」是否为 0，再看日志里对应 feature 那一行是
  `hook installed` 还是 `hook target missing`（后者说明这个 ROM 版本上靶子的类/方法名变了）。
- **重启按钮报「没能执行 su」**：设备没有 root，或者本应用还没被授权。
  在 root 管理器（Magisk / KernelSU / APatch）里给「澎湃补全计划」授权后重试。
- **注入侧的日志**：模块界面只能看到模块自身进程的日志。SystemUI / system_server 的日志在 logcat 里，
  按标签过滤：`adb logcat -s HyperExtend`。
